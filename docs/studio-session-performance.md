# Studio 登录验证与中台读取性能

## 2026-10-29 修复

`8571fbf` 已实现当前页优先、浏览器请求排队和空闲预取，但常规业务读取仍需加载完整快照。原生运行时的 SQLite 查询和 JSON 解析与登录验证共用事件循环；历史记录较大时，页面请求会阻塞 Studio 的会话校验。此前 Studio 的 8 秒总时限、连接复用和同会话在途合并不能消除这种阻塞。

本次保留首屏调度和所有业务内容，改为原生快照按 rowid 分批读取、解析，每批让出事件循环。完整读取前后仍比较全局 revision，变化时最多重新读取三次；业务写入的版本校验、事务和重试语义不变。每批以 64 行／1 MiB 为让出目标，不截断单条记录，不维持跨异步等待的 SQLite 游标或事务。D1 沿用原读取路径。

账号加入检查只读取成员记录；后台调度查找成员也不再读全库。业务页审计使用请求内 ID 索引，按倒序执行原权限判断，收集够最新 250 条可见记录后停止。不会先按数据库 LIMIT 截去不可见历史，也没有跨账号缓存授权结果。

分批读取同时限制为最多两个大快照，其余按到达顺序等待，避免多人访问时同时积累大量历史 JSON。仅明确读取成员的请求绕过该队列；异常也释放读取名额。限制的是快照构建过程，不是整个请求的内存或外部接口等待；业务版本校验和写入语义不变。

## 验证

- 全业务检查、TypeScript、隔离原生构建和 HTTP 回归通过。
- 快照测试覆盖负数／零／64 位最大 rowid、批次之间新增删除、revision 重读上限、过期提交拒绝和读取期间撤权。
- 8 类角色的审计输出与原算法一致，包含尾部 600 条私有历史和交错不可见记录。
- 隔离合成库包含 131,558,194 字节 JSON、15,670 条记录，最大单条约 1 MiB。并发 3 个业务读取和 20 个会话验证时，同一新代码关闭／启用分批读取的会话 p95 分别为约 1,432／12 毫秒；另一轮并行测试负载下约 2,046／18 毫秒。记录和账号字节哈希保持一致。
- 增加并发上限后的独立测试中，20 个业务读取全部完成；Node 堆限制为 768 MiB，实测峰值 RSS 约 655 MiB，会话 p95 67 毫秒，排队期间成员检查 94 毫秒完成。额外验证读取异常释放名额和成员快通道。结果是指定合成数据下的测量，不代表所有业务响应的固定内存上界。

以上为合成负载结果，不是线上员工浏览器验收。超大单条 JSON、结果组装及序列化仍可能短暂占用事件循环；不据此承诺所有请求永不超时。

源码提交与推送不代表部署。服务器发布记录须另行填写，并按项目规则保留一致性备份、核验原记录与附件。
