# Customer project API contract

No migration/initialization writes. Existing customer_account/order/customer_quote are read only. Team membership NEVER grants customer or quote access: project access intersects existing sales/service assignment. Types: lib/customer-projects.ts.

GET `customer-project-data` returns customers (with assignableMemberIds), teams, projects (with canWrite, canManageTasks, canManageAssignments, assignableMemberIds), items, rounds (with remainingScope), communications, tasks (with canManage, canSubmit, canReviewService, canReviewSales, reviewConfigurationValid), drawings, confirmations, quoteLinks, samples, dispatches, feedback, handovers, attachments, orders (safe production summary), quotes (authorized confirmed-version candidates only), members (id/name/role), canManageTeams, canWrite. Task permissions intersect the current active project, current assignment and existing customer write scope. These fields are read-only projections, never persisted. Internal-only staff get only own sample jobs, safe item snapshots, no project/quote/finance records.

All POST JSON schemas are strict. Updates use target `id,version`; append/create actions use UUID `token` except project/item/round/team save (token still required for creates). Result `{ok:true,item,idempotent?}`. Errors `{error}` with 400/403/409. All actions prefixed `customer-project-`:

Independent page entry API: POST `customer-project-entry-save` accepts `entryType` (`item`, `round`, `communication`, `task`, `drawing`, `confirmation`, `quote`, `sample`, `dispatch`, `feedback`, `handover`, `attachment`), `token`, `projectId`, optional `roundId`, and editable fields for that entity. Updates also send `id,version`. Field definitions are in `lib/customer-project-entries.ts`. These entries use the existing entity collections and can be added or edited on active, paused, cancelled, or archived projects. Business fields and relationships may be left empty; empty titles receive readable defaults. Quantities must be finite and nonnegative, without an artificial business maximum. Relationships, when supplied, must belong to the same customer/project and any referenced quote or order must be currently readable. Saving an independent entry does not create an automatic follow-up, release an order, move money, or impersonate an approval; task history records a configuration edit. Existing account/customer authorization, concurrency and idempotency checks remain in force.

Independent handovers have `independentEntry:true` and do not consume formal transferred quantities. The first independent edit of an existing formal handover retains its original execution record in `executionSnapshot`; subsequent edits preserve this snapshot, and formal transfer calculations continue to use it. The ordinary response and history omit this snapshot and payment details. Existing sample item/payment snapshots and real attachment storage keys cannot be written by clients. Attachment uploads require no project lifecycle or round prerequisite and retain file size/type checks. The workflow actions below remain available with their formal release/review rules.

Optional string fields default empty, arrays default empty where appropriate. Server checks internal staff, customer/round/item/file relations, version, financial paymentGate and approved selected drawings before release. All quantity scopes are positive integers. Team save is admin-only organizational metadata; no old records changed. Sample execution jobs remain separate `customer_project_sample` records, NEVER flow into existing bulk PMC quantities.

Project service owners support multiple existing customer-responsibility members. Every selected member must be active and already authorized to write for that customer; assigning staff does not grant customer, order, quote or finance access. New saves store `serviceMemberIds` and keep `serviceMemberId` equal to its first entry for existing single-owner task defaults. Reads of old projects fall back to the legacy ID without migration. An explicit empty array clears the service selection. Older forms submitting an unchanged legacy ID preserve all selected staff; attempting to replace a multiple-staff selection through the legacy field returns 409 and requires refreshing the form.

Project `serviceReviewerId` and `salesReviewerId` are optional task defaults: omission preserves the stored value, an explicit empty string clears it. Changing an existing project's teamId, salesMemberId or either default reviewer requires assignment-management authority; ordinary customer writers may edit other project fields and send unchanged assignments. Managers are the administrator, assigned project salesperson or a leader of the project's active team that still includes this customer, always intersected with current customer write access. `canManageAssignments` permits correcting assignments on paused/cancelled projects before reopening, including replacing inactive reviewers. Archived projects retain their existing administrator-only reopening rule. Task-management and task actions additionally require active project status. Creating a new project retains the existing customer-write rule. Defaults do not rewrite existing tasks.

Task flow: `open/returned → service_review → sales_review → done`. Either reviewer can return to `returned` with a required opinion. Resubmission restarts service review and increments `reviewCycle`. The follow-up owner and both reviewers must be active members with existing customer write access; the owner cannot review their own task. Both review roles may use the same authorized person, but each stage requires its own action. Administrator status does not substitute for the designated owner or reviewer. Assignment or role revocation takes effect immediately.

Managers create and configure tasks; new tasks must resolve both reviewers (explicit fields or project defaults) and cannot start completed or cancelled. Incomplete tasks may be updated to open or cancelled. Editing or cancelling a task under review requires `changeReason`; editing returns it to open and preserves its result and every review event. Cancellation preserves all original business fields and changes only state/history/metadata, so invalid legacy assignments do not prevent cancellation or get silently rewritten. Completed/cancelled tasks cannot be rewritten. Each update appends a `reconfigure` or `cancel` event. Only task-submit changes the result. Task-submit/task-review require UUID tokens and exact versions; current project scope and designated actor checks occur before token replay, with state/version checks after replay, so retries are safe without permitting new unauthorized actions.

`reviewHistory` is append-only: `{id,action:submit/approve/return/reconfigure/cancel,stage:followup/service/sales/configuration,actorId,actorName,at,comment,cycle}`. Submission events retain the submitted result in comment; both review stages retain their opinions. Old tasks are read with `reviewHistory:[]` and `reviewCycle:0` if absent, without writes. Old done tasks remain done. Old open tasks without valid review assignments need a manager to configure them before submission. Communication, drawing-change and sample-generated tasks copy current project reviewer defaults; absent defaults leave the task awaiting configuration, never implicitly completed. Every nonterminal task, including returned and both review stages, prevents project archival.

Bulk lines must have sourceStatus exactly 正式订单 and not a draft business workflow; code does not change sourceStatus for the user. Required sample approval at order-stage checks every affected item. before_production creates explicit handover task naming the configured production checkpoint; this release does NOT automatically block original PMC operations. Sample dispatch counts manufactured quantity once: repair/resend cannot be disguised as new delivery; establish an explicit revision/new sample run for newly manufactured samples and preserve original dispatch.

Attachment POST `customer-project-attachment` uses FormData(projectId,roundId,file,note,category?). Each file must be nonempty and at most 50 MiB (52,428,800 bytes); the standalone endpoint accepts up to 51 MiB including multipart overhead. `category` is `general` (the default when omitted) or `original-communication`; every other value is rejected. Old attachments without a category remain general. General attachments retain the existing PDF/images/office/CAD DWG DXF STEP STP IGES IGS STL/EML allowlist.

Original communication documents accept every extension and files without an extension. They are project-level records: `roundId` must be empty, and no item, round, approval, order or finance entry is created by uploading. Current project read/write authorization applies. The existing internal sample handoff grants file-level read access only through an assigned sample's explicitly selected drawing and that drawing's selected attachments, including original communication documents. It does not grant customer/project access or access to other original documents in the same project. Bytes are stored unchanged under a server-generated storage key; filenames are sanitized and truncated by Unicode code point. Repeating the same project/customer, category, round, filename, note and content hash returns the prior record without another write. Independent attachment entry edits preserve category and stored file fields; clients cannot set category or move an original document to a round.

GET `customer-project-file?id=...` checks current project access or the existing precise assigned-sample → selected-drawing → selected-attachment handoff. The same rule limits attachment metadata in the data response. Original documents always download as `application/octet-stream` with attachment disposition, `nosniff` and restrictive sandbox CSP, including HTML, SVG and executable extensions. GET `customer-project-history?projectId=...` returns scoped safe history and excludes quote content when quote authorization is missing. New quote links store identities and accepted evidence, not costs or prices.
