# Mastra P1：合成订单只读 API 与员工建议工作台

本目录延续 `codex/mastra-local-validation` 的隔离实验。原 P0 实验保留在 [`examples/mastra-local`](../../examples/mastra-local/README.md)，本目录新增 P1 API、真实 Mastra Agent 工具循环和员工建议展示。验收结果见 [ACCEPTANCE.md](./ACCEPTANCE.md)。

全部订单、客户和员工来自 `fixtures.mjs`，没有真实业务数据。Agent 使用脚本模拟模型；生成的是独立建议记录，不会创建正式协同任务或修改订单。页面不提供批准、保存、派发或业务写回。

## 运行

从本目录执行，Node 至少 22.13，本轮验证版本为 24.19.0：

```powershell
npm ci --no-audit --no-fund
npm test
npm run preview -- --synthetic
```

按终端 `PREVIEW_READY` 输出的 `url` 打开页面。服务只监听 `127.0.0.1` 的系统分配端口，不使用 8787。选择模拟员工 A 或 B，点击“进入查看”，分别看到 4 条授权订单和 2 条跟进建议。

`Ctrl+C` 结束本次预览。预览创建的合成建议库保留在系统临时目录，方便重新启动验证：

```powershell
npm run preview -- --synthetic --resume "<上次 PREVIEW_READY 的 directory>"
```

`--resume` 仅接受系统临时目录下带有实验标识的 `doon-mastra-p1-*` 目录，不接受任意数据库路径。每次启动均对两个合成员工重跑模拟检查，通过建议内容幂等补齐部分结果；已有记录保持不变。`--prepare-only` 完成准备后立即退出，供跨进程测试使用。

测试自动创建并清理自己的临时目录。预览目录可能被系统清理，不作为正式持久存储。安装只使用本目录的依赖与 lockfile，不需要在业务根目录执行安装、构建、部署或迁移。

## 数据与权限边界

- `policy.mjs` 在内存中编译当前分支的 `lib/domain.ts` 并调用真实 `canRead`。编译入口只允许该纯规则文件，禁止新增依赖，不加载业务 store、运行时、数据库或附件目录。
- 本轮覆盖内部员工按客户范围读取订单；未覆盖完整登录、CRM、任务/团队权限、供应商门户及所有角色组合。停用身份和供应商身份直接拒绝。
- HTTP 会话在服务端绑定模拟身份，业务 API 不接受调用者指定 `memberId` 或 `actorId`。每次读取和建议展示都重新检查当前来源权限。
- `POST /api/demo-session` 只是公开可选的合成身份演示，**不是生产认证**。本原型不能作为公网服务部署，也不能将数据源替换成真实数据后直接使用。
- 订单 DTO 明确列出允许字段，排除邮箱、附件键、私有备注等；分页数量为 1–50，游标绑定身份、数量和可见来源指纹。权限或来源变化使旧游标失效。
- 建议保存来源 ID、版本、指纹及运行标识。来源变化时展示“来源已更新”，清空旧理由和动作；撤销来源访问后不再返回建议。
- 建议库是新建的独立 SQLite，HTTP 查询连接以只读模式打开。只有实验启动阶段的 Agent 可向该合成库新增建议。数据库、缓存、会话、日志都不提交 Git。
- 预览不加载 `.env`，不读取模型密钥；检测到列出的业务运行配置时会拒绝启动。HTTP 工具只接受本机非 8787 地址，拒绝重定向；静态资源没有 CDN。

页面中的时间与日期比较固定于合成场景 `2026-10-15 09:00 Asia/Shanghai`，不是实时订单时钟。`syn-run-<员工>-20261015` 是此固定场景的运行标识，不代表生产唯一执行 ID。归档订单可作为只读来源查询，但不会生成跟进建议。对已过去交期只提示核对履约情况，不判定订单实际逾期。

## 接口与链路

| 接口 | 用途 |
| --- | --- |
| `POST /api/demo-session` | 仅在内存建立合成员工会话，唯一允许的 POST |
| `GET /api/me` | 当前模拟身份 |
| `GET /api/orders?limit=20&cursor=...` | 授权订单白名单字段与分页 |
| `GET /api/orders/:id` | 授权来源详情，越权与不存在均为 404 |
| `GET /api/suggestions` | 当前员工可见建议，重新检查来源权限与版本 |
| `GET /health` | 合成服务标识与状态 |

业务 POST/PUT/PATCH/DELETE 返回 405。主项目 `/api/*` 和 8787 路由没有注册这些实验接口。

生成链路为：真实 Mastra Agent → schema 工具 → 本机 HTTP 只读 API → 当前项目 `canRead` → 合成订单 DTO → 来源重新校验 → 独立合成建议库 → 员工只读页面。

`mock-model.mjs` 模拟模型输出，`rules.mjs` 确定性选择建议；这证明 SDK、工具和 API 能协作，不证明大模型判断质量。工具在应用层验证身份、来源版本和允许的规则，不能按任意模型文字写入业务数据。读取工具目前限制单页 50 条，发现后续游标会中止生成；大数据量的完整分页与令牌预算留待下一阶段。

## 验证与下一阶段

`tests/policy.test.mjs` 检查权限、DTO、分页和数据不变；`tests/http.test.mjs` 检查真实 HTTP/Agent、来源失效、拒绝写入、完整及部分建议恢复；`tests/sdk.test.mjs` 额外检查 generate/stream、无记忆新上下文、工具审批和 libSQL 跨进程恢复。原 11 项集成与 5 项源码检查仍用原实验命令运行，不能用本目录测试数替代。

后续按以下门槛逐步推进；均未计入本轮通过项：

1. **真实模型**：按暂定 DeepSeek V4 Pro 选择官方可用的模型 ID、适配器及 thinking 配置，用合成订单验证普通/流式工具调用、审批暂停后跨进程恢复、超时与限流；记录实际成功率、延迟、输入输出用量和费用。内部 reasoning 标记恢复测试不证明供应商协议兼容。
2. **项目权限接入**：将服务端真实会话映射为最小权限身份，复用完整订单/团队/CRM 权限链路；为各角色、禁用账号、撤销授权、跨租户或客户访问制定负例矩阵。不得让模型或浏览器自由选择真实员工身份。
3. **云服务器试点**：先只读核实 Ubuntu/Node 版本、现有进程、内存、磁盘、数据库与服务基线，再决定同机运行。建议独立用户、独立状态目录、单 worker、并发 1、队列与资源上限；2 vCPU/4 GiB 共享实例的可用容量必须实测，交换空间不作为运行内存容量。临时实验不替代 systemd、反向代理或故障监控方案。
4. **持久化与恢复**：以独立测试库验证最终存储方案；若使用 PostgreSQL，验证迁移、事务、权限、备份还原及进程异常退出恢复。SQLite/libSQL 成功不等于 PostgreSQL 已通过，也不要求本轮在小实例上新增数据库服务。
5. **业务写入与调度**：另行实现可信审批人、动作内容绑定、来源版本校验、事务幂等账本和不可变审计，再验证真实计时触发、重复触发、宕机补跑、企业微信回执。必须在允许业务写入之前完成这些验收。

云试点建议先约定可测门槛：相同负载下正式服务 P95 延迟退化不超过 10%，无新增 5xx/OOM，持续负载无明显交换抖动，并保留约 768 MiB 可用内存；这些是待确认的初始试点预算，不是本轮已测得的数据。未满足时降低并发或拆分 Agent worker，不能以“本地测试通过”直接批准上线。
