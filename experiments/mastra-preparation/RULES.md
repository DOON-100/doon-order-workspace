# 首条采购闭环：准备阶段业务规则与字段映射

日期：2026-10-17（Asia/Shanghai）。设计依据：[Agent 系统设计 v0.4](../../docs/agent-system-design.md)。代码基线：合并提交 `199624df584ccf50331387c5034321e8c725a9cc`，纳入主线 `a35d40a80f1a59e249d4f80876187a41613f135c`。

本文是可执行实现之前的规则清单，用于编制合成 JSON、标准答案及后续验收。只读核对源码，不表示业务规则已新增实现或测试通过；没有接入真实采购、账号、附件或数据库。准备阶段只保存文档与合成资料，不执行模型、业务写入、派单或消息发送。

## 1. 标记与适用范围

- **已有源码规则**：当前代码可直接证明的字段、计算或准入行为；引用源码不等于已验证完整生产链路。
- **新增合成假设**：为了确定标准答案而明确给出的测试条件，只适用于合成资料，不推定真实业务已具备相应关系或凭证。
- **待确认**：真实来源或业务政策尚未确定。可以用标明版本的合成假设开展 A、B1、C1/C2；不能据此放行对应真实能力。

规则 ID `R01`—`R14` 稳定供场景引用。以下扩展字段名称表达契约含义，后续 schema 可确定具体结构，但不得悄悄改变数量、授权或关闭语义。合成主体、来源和凭证使用显式合成标记，不填入真实名称、账号、群标识或私有附件路径。

## 3. 稳定业务规则

### R01 — 采购行身份与唯一匹配

**已有源码规则：**首次导入 ID 由文件哈希、工作表及行号生成；后续唯一 `purchaseKey` 匹配时保留旧 ID。已有行或新批次中相同组合出现歧义时不能自动覆盖；三字段匹配键不是上游不可变行 ID。[导入 ID](../../lib/purchase-import.ts#L22)、[匹配与保留 ID](../../lib/purchase-api.ts#L32)

**新增合成假设：**正常场景采购行使用固定合成 ID，版本变化不换 ID。重复组合、拆行／合行或来源身份无法确认的场景标为待核查，不据此新增多个自动催办事项。真实稳定行标识及继承政策待 D01 确认。

### R02 — 来源版本、时效与一致批次

**已有源码规则：**来源导入拒绝早于当前 `sourceAsOf` 的文件，提交检查 `expectedSourceVersion`；跟进与收货另检查对象版本。`sourceAsOf` 是日期，不是模型调用时间。[来源校验](../../lib/purchase-api.ts#L34)、[提交校验](../../lib/purchase-api.ts#L45)

**新增合成假设：**场景显式给出观察时钟、相关来源版本、关联／分配版本和完整性。是否过旧使用该场景明确的策略输入，不硬编码为生产阈值。相关依赖变化则旧当前结论失效，历史依据继续按权限保留；无关记录更新不等于采购内容变化。未知时效或混合批次不能产生确定欠交／关闭结论。真实时效规则待 D04 确认。

### R03 — 未知收货不当零

**已有源码规则：**新导入 `balanceKnown=false`，虽然存储 `received=0/returnPending=0`，`remaining` 仍返回 `null`；需先核对基数才能登记普通收货、退货或补回。[初始化](../../lib/purchase-import.ts#L22)、[未知未交](../../lib/purchases.ts#L8)、[基数门禁](../../lib/purchase-api.ts#L69)

**合成标准答案：**未知基数只能形成收货待核查，不能声称全部未交、零实收或已齐料。数据中同时保留“未知”和“已确认零”两种反例。真实基数证据待 D02 确认。

### R04 — 净合格收退货守恒，不重复扣减

**已有源码规则：**`received` 是已扣减退货后的净合格累计口径；`remaining=max(0,quantity-received)` 已含待补数量，`full` 还要求 `returnPending=0`。[纯计算](../../lib/purchases.ts#L7)、[事件计算](../../lib/purchase-api.ts#L65)

| 事件 | 净实收变化 | 待补变化 | 条件 |
| --- | --- | --- | --- |
| `opening/correction` | 设置累计基数，不是追加 | 设置待补基数 | 初次核对与后续更正分开，必须留依据 |
| `receipt` | 加本次量 | 不变 | 不超过 `quantity-received-returnPending` |
| `return` | 减本次量 | 加本次量 | 不超过当前净实收 |
| `replacement` | 加本次量 | 减本次量 | 不超过当前待补 |

**合成标准答案：**每步满足 `0≤received≤quantity`、`0≤returnPending≤quantity-received`。不得再从净值扣一次退货，或把待补再次加到未交量。现有同类凭证检查与 token 防重复只能作为本模块行为参考，不能据此宣称未来 Agent 动作已具备内容绑定幂等。[重复检查](../../lib/purchase-api.ts#L59)

### R05 — 单位、精度与可互换范围

**已有源码规则：**数量最多四位小数；已核对收货后，来源单位变化或新数量无法容纳既有收货／待补时需要人工核对。代码没有通用单位转换模型。[导入精度](../../lib/purchase-import.ts#L21)、[单位变更](../../lib/purchase-api.ts#L35)

**新增合成假设：**首例全用同规格、同批次“件”。异单位场景须给明确、已确认、有版本的换算关系；缺失、失效或不可互换时不相加、不判齐料。禁止由名称相似猜测“件／套／箱”等关系。真实转换及物料范围待 D04、D03 确认。

### R06 — 采购义务缺口不同于订单需求缺口

**已有源码规则：**采购未交按采购 `quantity` 与净实收计算；`customerOrder` 只提供文本关联，未表达订单物料需求。[采购字段](../../lib/purchases.ts#L5)

**新增合成假设：**主例独立给出采购应交160件及到期、验收口径，净合格100件，净合格履约数量缺口60；A、B各需80件只是另一组需求事实。该差额不单独证明“供应商未送货”或供应商归责：例如60件已到待检，先内部核验，不能将其计入净合格量，也不能直接按差额催供应商再送60。催交须同时具备适用采购义务、到期、收货／验收状态及相应原因依据；未核清原因时保持待核查。

**对照标准答案：**采购仅应交100且已收合格100，即使两订单仍共需160，也不得催供应商补“欠交60”。需另查采购覆盖或分配，不能把需求缺口转成已有供应商义务。依据：[设计第8.2及22.5节](../../docs/agent-system-design.md)。真实义务范围及验收口径待 D01、D02、D03 确认。

### R07 — 多订单分配不重复计量

**现状：**已核对的采购／PMC 模块没有完整 BOM 需求与多订单数量分配模型。`customerOrder` 与订单号相等不证明已分配数量。

**新增合成假设：**独立分配证据记录采购行、物料／批次、订单、单位、数量和版本。同一净合格量只能被计入一次；100件分配A80/B20，A仅该物料满足，B仍缺60。没有确认分配则两订单均为分配待核查，模型不得选优先级。退货使分配依据不足时标记受影响关系待核查，不自动挪用其他订单份额。真实权威来源待 D03 确认。

### R08 — 正式复期、内部预计与有效承诺分离

**已有源码规则：**`dueDate` 源自预计交货日期；`promisedDate/expectedDate/nextFollowupDate` 是独立跟进字段。`purchaseStatus` 的逾期日期优先取 `expectedDate`，因此状态“交期已逾期”本身不证明供应商违反承诺。[日期字段](../../lib/purchases.ts#L4)、[状态优先级](../../lib/purchases.ts#L18)

**新增合成假设：**独立承诺记录行、批次、日期、数量、单位及数量语义（追加／累计目标／剩余未交）、确认状态和依据。未确认、含糊或冲突承诺不能生效、延后核查或覆盖正式复期。场景固定观察日期和 `Asia/Shanghai`；不使用运行当天日期改变标准答案。真实到期、工作日历与确认权限待 D04、D05 确认。

### R09 — 审核、源关闭与归档准入

**已有源码规则：**`sourceClosed` 对任何不等于“未关闭”的值视为关闭；收货接口要求“已审核”、未源关闭。已归档仅允许实际退货恢复跟进；归档须足量且无待补。[状态规则](../../lib/purchases.ts#L10)、[收货门禁](../../lib/purchase-api.ts#L61)、[归档条件](../../lib/purchase-api.ts#L81)

**合成标准答案：**正常采购明确填“已审核／未关闭／active”。缺失或未知状态不自动猜正常，先待核查；源关闭、未审核、归档分别作为反例。源关闭不等于已履约，归档也不自动证明所有关联订单齐料。

### R10 — 区分采购关闭、单物料满足、整单齐料与 PMC 已核对

**已有源码规则：**`full` 仅证明其数量条件；采购归档还有状态条件。`PmcReview.status=done` 表示已核对，`orderVersion` 改变后变为需复核，不代表已生产或已验收。[齐货](../../lib/purchases.ts#L9)、[PMC 状态](../../lib/pmc.ts#L15)

**新增合成假设：**采购事项关闭需本范围义务、合格履约证据、单位及来源条件全部满足；原字段不提供完整验收证据时，在合成层显式提供或标缺失。到货、待检、验收合格分别记录；100件已核净合格加60件待检，不能按原始到货160件关闭。订单单物料足量后仍核对其他必需物料及条件，未给完整需求清单时只能回答“该物料满足／整单齐料待核查”。承诺或口头“完成”不能代替实收验收。真实关闭标准待 D02、D06 确认。

### R11 — 唯一采购事项、范围重叠与再次发生

**新增合成假设：**按稳定采购行 ID、异常类型和规范范围复用非终态事项；多个订单通过独立影响关系引用同一个采购事项。整行与批次范围重叠未消除时不重复催办。跨天、换负责人、规则换版不复制事项。关闭后有新异常才建新 `caseId` 并引用 `previousCaseId`；旧未决动作仍须核对，不借新 ID 重发。该 Agent 账本行为尚未实现，依据：[设计第7节](../../docs/agent-system-design.md)。

### R12 — 可信身份、岗位委派与最小披露

**已有源码规则：**采购维护使用 `admin/pmc`；采购读取采用全读权限或可读订单号关联，不是独立供应商披露授权。成员停用仍须由可信入口额外检查；`buyer/supplier` 名称不构成账号身份。[读取范围](../../lib/purchases.ts#L23)、[维护权限](../../lib/purchase-api.ts#L9)、[成员角色](../../lib/domain.ts#L2)

**新增合成假设：**采购岗位用独立 assignment 映射合成内部成员；人工请求默认 `onBehalfOf`，只有服务端认可的策略与 grant 才可建立 `policyAuthorizedRoleTask`。持久记录发起人、范围、有效期和策略／委派版本；目标岗位可独立查证不等于调用方可读全部结果。任务摘要按独立披露策略生成，多来源正文保存 `sourceDeps`；模型每次出站前重验上下文。这些不是现有角色规则自动提供的能力。真实职责与披露策略待 D05 确认。

### R13 — 承诺替代、乱序与历史留痕

**现状：**正式采购跟进字段及其审计存在，但未提供设计中的完整 `agent_commitment` 状态模型。

**新增合成假设：**仅已确认、适用同一范围的承诺可以明确替代旧承诺；部分数量或批次替代不覆盖其余范围。保留旧承诺及已发生失约，新承诺不关闭风险。未确认回复不延后旧有效核查计划。终态事项收到旧回复仅留痕，不推进新事项或发起新消息。原始回复、核实证据与执行回执仍按当前读取权限保留，不能因来源后来更新抹掉已发生事实。真实确认与升级政策待 D04、D05、D06 确认。

### R14 — 影子模式与副作用门禁

**本阶段约束：**准备材料不是执行许可；不新增真实派单、外部消息、正式复期或库存写回，也不启动业务服务。B1/C1/C2 后续只在隔离环境、独立合成 Agent 账本内验证。B2 真实只读、内部接管、D 外部发送、E 正式变更分别通过其授权门槛；未配置派发额度默认不派发。

**后续合成标准答案：**暂停阻止新自动许可；在途结果未知不伪报取消、不换动作 ID 重发；已完成同键动作查询既有回执，不重新执行。正式写入仍须业务端内容绑定、权限、版本与幂等检查，不能把现有 P1 实验业务写入口统一405或采购事件 token 检查当作这套能力已验收。依据：[设计第14、16、22节](../../docs/agent-system-design.md)。

## 4. 首条闭环的数量锚点

这些数值是合成假设，原业务接口不执行；场景以独立快照及证据表达变化。

| 快照 | 采购应交 | 净合格 `received` | 待补 `returnPending` | 未交 `remaining` | 可给出的结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| 初始已核对 | 160 | 100 | 0 | 60 | 一个采购履约核查事项；有到期及欠交原因依据才推进催交。A/B各需80，分配80/20后B该物料缺60 |
| 确认退货10 | 160 | 90 | 10 | 70 | 退货已扣净值；原分配需复核，不能自动把影响全算给某订单 |
| 普通收货60 | 160 | 150 | 10 | 10 | 待补10未完成，不能关闭 |
| 退货补回10 | 160 | 160 | 0 | 0 | 数量条件满足；还需有效验收、范围与关闭证据 |
| 对照：实际只采购100 | 100 | 100 | 0 | 0 | 两订单总需160仍有需求缺口，但本采购行不欠交，不催供应商补60 |
| 对照：另有60件已到待检 | 160 | 100 | 0 | 60 | 先内部验收核查；不计待检数量为净合格，不断言供应商未送60，不关单 |
| 对照：基数未知 | 160 | 底层可为0，语义未知 | 未知 | `null` | 收货待核查，不计算确定欠交或齐料 |

## 5. 六类待确认事项与阶段阻断

下列责任岗位为建议协调方，不是已获用户确认的个人指派。未决项不阻止明确假设下的合成开发；它们阻止将该假设升级为真实事实或权限。

| ID | 待确认事项及应形成的决定 | 建议责任岗位 | 阻断的后续能力 |
| --- | --- | --- | --- |
| D01 | 上游采购稳定行标识；重复组合、拆合行继承；采购义务及适用批次的权威来源 | 采购负责人、源系统维护人员 | B2 可靠来源映射；真实采购事项去重及接管；E 涉及行身份／义务的变更 |
| D02 | 历史净合格基数、验收、退货、冲销与纠正的权威证据；净值还是毛值、如何避免重复扣减 | 仓储／收货、质量、采购负责人 | B2 确定性履约判断；真实 C 关闭与订单风险核算；E 收退货写回 |
| D03 | BOM／需求、物料规格与批次、订单关联及分配的权威来源；共料不足时谁确认分配 | PMC、采购、物料计划／工程岗位 | B2 确定性齐料判断；真实 C 影响归并与整单风险解除；不妨碍仅展示待核查 |
| D04 | 单位转换、精度、互换限制、来源过旧阈值、到期时点及工作日历 | PMC、采购、质量／物料岗位 | B2 相关数量与时效结论；真实 C 自动到期核查；D 自动催交频率与时段 |
| D05 | 采购／PMC主责和替补、两类委派依据、允许摘要、承诺确认人与供应商身份绑定 | 业务负责人、采购／PMC负责人、权限管理员 | B2 专用授权；真实 C 派单及跨岗披露；D 对外发送；E 审批执行 |
| D06 | 采购事项／单物料／整单各自关闭证据、失约升级与重新发生标准、存量接管额度及结果不明动作的核对责任 | 采购负责人、PMC、质量、业务负责人 | 真实 C 关闭、升级和存量接管；D 结果不明消息处置；E 变更后的对账与纠正 |

本目录已提供与上述规则关联的合成场景，列出输入、标准答案和拒绝原因；未覆盖部分在 JSON 的 `coverageGaps` 中明示。后续把这些向量转为实现级验收，运行检查与通过情况单独记录。本文不把任何未实现、未执行或待确认项计为通过。
