# Mastra 准备阶段资料

日期：2026-10-17。分支：`codex/mastra-local-validation`。当前设计依据：[Agent 系统设计 v0.5](../../docs/agent-system-design.md)及[阶段一实施清单](../../docs/phase-one-implementation-checklist.md)。

本目录是首条采购内部闭环的设计输入与合成验收向量，不是可运行的 Agent 或业务导入包。全部账号标识、订单、采购行、数量、凭证和时间线均为合成数据；不包含真实账号、密码、模型密钥、业务快照或附件。

历史准备阶段完成范围为：同步已确认的主线基线、纳入 v0.4、整理字段与规则、提供可核对的合成输入及预期结果。本次 v0.5 仅明确固定程序优先的阶段一范围和后续顺序，没有新增实现或运行验收。真实业务契约仍需确认，当前阶段一及 A/B/C 路线的实现与运行验收没有因这些资料完成而自动通过。

## 当前阶段一的优先约束

1. 固定程序能够完成的任务优先复用固定程序。已整理的 19 个数据工具入口本质都是固定程序；先登记全部入口并审计顶层副作用、默认正式路径、owner 代行身份及预览/提交边界，再对首批选定入口逐项封装和验收，不直接把 CLI 暴露为员工 API。可以使用受控按钮、明确参数和固定任务链，不必等待全部迁移，也不强制迁入 Mastra 或改成 processors。
2. 只有确需理解自然语言、非标准资料或模糊语义时才加 LLM 辅助。LLM 只形成有来源位置和版本的候选、说明或草稿；单次提取不必采用多 Agent，也不以模型评测阻塞无模型的确定性功能。
3. 所有受 LLM 判断影响的业务对象、参数、内容和动作先由有权限人员核验，再交给固定程序。核验绑定来源版本/指纹、完整载荷及哈希、目标、审核身份与权限、规则版本和有效期；执行前重新检查。未核验、关键未知、来源冲突或绑定失效时，阻止相应写入、发送及业务状态推进；拒绝、暂缓、超时或未回复均不视为批准。
4. 已授权且输入充分的固定规则任务按既有策略执行，不因此增加逐次人工确认；原业务规则要求的审批仍保留。自主分析、模型委派和模型自行推进业务是后续候选，不能由本目录资料默认开放。

本目录的采购闭环可以完全用规则、人工录入承诺、持久任务和到期核查实现。可选 LLM 只用于解析非标准回复等确需理解的输入，候选仍经人工核验。任务范围与验收逐项记录在[阶段一实施清单](../../docs/phase-one-implementation-checklist.md)，规划不等于已实现。

## 第一条闭环

采购闭环候选目标是“确认采购欠交 → 唯一采购事项及订单影响关系 → PMC 核查与采购内部任务 → 人工确认承诺 → 到期重读事实 → 按采购义务验证采购事项，再分别核算订单风险”。该链可以确定性实现，不因使用“岗位”或“任务”就需要岗位 Agent。是否列入阶段一首批交付由实施清单确定；准备资料只描述这条链，不创建真实事项或执行这些动作。

主例采用同一合成物料和“件”：采购应交 160，已核净合格 100，两个订单各需 80，经确认分配为 80／20。净合格履约缺口为 60，订单 B 的该物料缺 60，采购事项只有一份。尚未核清送达、验收与归责时，只形成内部核查候选，不直接催供应商。订单 A 仅该物料已满足，不能仅凭这一物料判整单齐料。

必备反例是采购只订 100 且已合格收齐，订单需求和分配仍为 80／80、80／20。此时订单 B 仍缺 60，但采购没有欠交，不能向供应商发出无依据催交。

现有 `received` 是净合格累计数，退货登记已经减少它；`remaining` 是已知基数下的 `max(0, quantity - received)`。`returnPending` 已包含在未交量内，不能再从净值扣退货或给未交量加待补。新导入的 `balanceKnown=false, received=0` 表示基数未知，不能当作已确认零收货。

订单—采购多对多关系、物料需求、分配依据、验收证据、承诺及任务授权是本目录的独立合成契约；原资料中的 Agent 命名不要求实施时必须调用模型。当前 `customerOrder` 文本引用、业务员姓名、PMC 的“已核对”状态都不能替代这些契约。

## 合成资料的读取与覆盖

JSON 含 20 个独立场景，固定观察时点为北京时间 `2026-10-15 10:00`。每个输入由 `base` 与该场景的 `overrides` 合成；每个标准答案由 `expectedBase` 与 `expectedOverrides` 合成。普通对象递归合并，数组整体替换，`null` 明确表示未知或不可用；不得从上一场景继承执行结果。

`sourceProjection` 只投影现有字段；`plan` 保存拟新增的合成契约。`declaredAllocationBaseQuantity` 只是所提供分配记录的声明总量，须通过 `allocationValid` 才能作为有效分配；未知或超额分配不会成为订单已满足的依据。

场景引用 14 条规则中的 13 条，覆盖数量、单位、分配、来源版本、承诺、事项复用、暂停及撤权等代表性情况。JSON 的 `coverageGaps` 明列 10 类未覆盖或需扩展项，包括 R09 的审核／关闭／归档组合、完整授权矩阵、故障恢复，以及独立原因证据齐全后的供应商催交正例。引用某条规则不代表该规则已完整覆盖，更不代表通过运行测试。

## 使用边界与后续顺序

合成资料使用固定观察时点，标准答案不随系统日期变化。扩展字段不写进正式 `Purchase`，JSON 不直接传入现有导入或写入 API；静态校验通过只表示资料内部一致，不证明这些目标行为已经实现。

1. 由业务负责人确认 RULES 中的数量、来源、关联、关闭及授权问题；暂未确认时只使用明确的合成假设。
2. 按 v0.5 阶段一清单先复用固定程序，建立所选任务需要的显式输入、受控事实投影、完整分页、授权、预览与校验；把本目录适用向量转为实现级测试。A/B1 的确定性与授权部分按需复用，不等待模型链路。
3. 确有语言理解需求才加入 LLM 候选、来源及出站控制和人工核验；未经核验或关键未知未解决不进入业务执行。模型不可用时保留手工确认输入，已授权固定规则任务继续按策略运行。
4. 所选场景需要持续采购跟进时，再按 C1/C2 建立独立事项、任务、承诺、调度和恢复；可完全用规则实现。自主 Agent 与多岗位模型编排属于后续候选；供应商通道及正式业务动作仍分别满足 D/E 对应授权和验收门槛。

本次文档修订不连接业务数据库，不读取真实附件或凭据，不构建、部署、停止、重启或修改 8787 服务，不执行导入、维护、备份同步和其他运行脚本；只读健康核验与功能开发、业务写入及部署分别记录。文档同步与正式部署分开，不能由 Git 操作推定功能已上线。本目录 Agent 相关资料在测试分支维护，普通业务功能遵守项目 `main` 分支规则；本次没有新增模型调用，保留既有累计费用和请求限额。
