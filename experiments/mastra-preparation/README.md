## 第一条闭环

首个目标是“确认采购欠交 → 唯一采购事项及订单影响关系 → PMC 核查与采购内部任务 → 人工确认承诺 → 到期重读事实 → 按采购义务验证采购事项，再分别核算订单风险”。准备阶段只描述这条链，不创建真实事项或执行这些动作。

主例采用同一合成物料和“件”：采购应交 160，已核净合格 100，两个订单各需 80，经确认分配为 80／20。净合格履约缺口为 60，订单 B 的该物料缺 60，采购事项只有一份。尚未核清送达、验收与归责时，只形成内部核查候选，不直接催供应商。订单 A 仅该物料已满足，不能仅凭这一物料判整单齐料。

必备反例是采购只订 100 且已合格收齐，订单需求和分配仍为 80／80、80／20。此时订单 B 仍缺 60，但采购没有欠交，不能向供应商发出无依据催交。

现有 `received` 是净合格累计数，退货登记已经减少它；`remaining` 是已知基数下的 `max(0, quantity - received)`。`returnPending` 已包含在未交量内，不能再从净值扣退货或给未交量加待补。新导入的 `balanceKnown=false, received=0` 表示基数未知，不能当作已确认零收货。

订单—采购多对多关系、物料需求、分配依据、验收证据、Agent 承诺及委派授权是本目录的独立合成契约。当前 `customerOrder` 文本引用、业务员姓名、PMC 的“已核对”状态都不能替代这些契约。

## 合成资料的读取与覆盖

JSON 含 20 个独立场景，固定观察时点为北京时间 `2026-10-15 10:00`。每个输入由 `base` 与该场景的 `overrides` 合成；每个标准答案由 `expectedBase` 与 `expectedOverrides` 合成。普通对象递归合并，数组整体替换，`null` 明确表示未知或不可用；不得从上一场景继承执行结果。

`sourceProjection` 只投影现有字段；`plan` 保存拟新增的合成契约。`declaredAllocationBaseQuantity` 只是所提供分配记录的声明总量，须通过 `allocationValid` 才能作为有效分配；未知或超额分配不会成为订单已满足的依据。

场景引用 14 条规则中的 13 条，覆盖数量、单位、分配、来源版本、承诺、事项复用、暂停及撤权等代表性情况。JSON 的 `coverageGaps` 明列 10 类未覆盖或需扩展项，包括 R09 的审核／关闭／归档组合、完整授权矩阵、故障恢复，以及独立原因证据齐全后的供应商催交正例。引用某条规则不代表该规则已完整覆盖，更不代表通过运行测试。

## 使用边界与后续顺序

合成资料使用固定观察时点，标准答案不随系统日期变化。扩展字段不写进正式 `Purchase`，JSON 不直接传入现有导入或写入 API；静态校验通过只表示资料内部一致，不证明这些目标行为已经实现。

1. 由业务负责人确认 RULES 中的数量、来源、关联、关闭及授权问题；暂未确认时只使用明确的合成假设。
2. 按 v0.4 A/B1 建立受控事实投影、完整分页、授权与模型出站校验，并把本目录向量转为实现级测试。
3. 再按 C1/C2 建立独立 Agent 事项、任务、承诺、调度和恢复；供应商通道及正式业务动作分别留在 D/E。
